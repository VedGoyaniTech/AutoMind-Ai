============ Agetic AI ===================

You are implementing a production-safe, controlled Agentic AI layer in the existing AutoMind AI / Project-V application.

Do not replace the current RAG, pricing, EMI, vehicle search, voice, gallery, feedback, authentication, database, or frontend modules. Reuse them as typed tools behind one central Agent Orchestrator.

The target architecture is:

```text
React Chat and Voice UI
        ↓
FastAPI Chat Route
        ↓
AgentOrchestrator
        ↓
Planner
        ↓
Typed Tools
        ↓
Verifier
        ↓
Structured Agent Result
        ↓
LLM Explanation using verified facts only
        ↓
SSE Streaming Events
        ↓
Chat Cards, Gallery, Reference Cards, Follow-up Chips
```

The existing project may contain files that were not listed in this prompt. First scan the entire current repository. Treat listed paths as known integration points only, not a complete file list.

Important product constraints:

- Do not add paid third-party APIs.
- Keep local pricing, RTO, insurance, fees, and EMI calculations deterministic.
- DuckDuckGo may be used only for research/reference discovery through existing project functionality.
- Do not trust DuckDuckGo search-result snippets as facts without validating actual destination URLs/content.
- Do not let the LLM invent prices, tax, launch dates, vehicle names, specifications, or references.
- Do not expose chain-of-thought or internal planner reasoning to users.
- Show short user-safe status messages only, such as “Checking local pricing rules” or “Comparing shortlisted cars.”
- Do not delete existing modules or break existing endpoints.
- Preserve all existing chat, authentication, database, gallery, feedback, voice, and RAG behavior.

# PART 3 — Agent State and Typed Schemas

Create typed schemas for:

## 3.1 Agent request

```python
AgentRequest:
  conversation_id: optional integer/string
  user_id: required authenticated user identifier
  message_id: optional
  message: string
  locale: optional string
  conversation_context: list of safe previous messages
```

## 3.2 Extracted entities

```python
ExtractedEntities:
  manufacturer: optional string
  model: optional string
  variant: optional string
  city: optional string
  state_code: optional string
  fuel_type: optional string
  body_type: optional string
  launch_year: optional integer
  requested_year: optional integer
  request_type: optional enum
  down_payment: optional decimal
  down_payment_percent: optional decimal
  loan_amount: optional decimal
  annual_interest_rate: optional decimal
  tenures_years: list of integers
  budget: optional decimal
  comparison_targets: list of vehicle references
  language: optional enum
```

## 3.3 Intent enum

Support at least:

```text
casual
vehicle_search
vehicle_details
yearwise_launches
vehicle_category
vehicle_comparison
on_road_price
emi
price_and_emi
upcoming_vehicles
historical_vehicle_lookup
gallery_request
sources_inquiry
unsupported_or_unclear
```

## 3.4 Planner output

```python
AgentPlan:
  intent: AgentIntent
  extracted_entities: ExtractedEntities
  steps: list[PlannedStep]
  needs_follow_up: bool
  follow_up_question: optional string
  follow_up_fields: list[string]
  confidence: float
```

A planned step must contain:

```python
PlannedStep:
  step_id: string
  tool_name: enum
  input: typed schema
  depends_on: list[string]
  purpose: safe short text
```

## 3.5 Tool result

Every tool returns:

```python
ToolResult:
  tool_name: string
  success: bool
  data: typed data or null
  warnings: list[string]
  sources: list[SourceReference]
  error_code: optional string
  user_safe_error: optional string
  executed_at: ISO datetime
```

## 3.6 Source reference

```python
SourceReference:
  title: string
  url: valid HTTP/HTTPS URL
  domain: string
  source_type: enum:
    local_database
    local_rule
    official_manufacturer
    trusted_automotive_publication
    web_research
  retrieved_at: ISO datetime
  published_at: optional ISO date
  confidence: enum high/medium/low
```

Never create fake citations. If a valid URL/title is unavailable, do not include a source reference.

## 3.7 Structured final result

```python
AgentResponse:
  kind: enum:
    text
    follow_up
    pricing_quote
    comparison
    vehicle_details
    vehicle_launches
    gallery
    error
  answer_text: string
  pricing_quote: optional object
  emi_options: optional list
  comparison: optional object
  vehicles: list
  gallery: optional object
  sources: list[SourceReference]
  follow_up: optional object
  warnings: list[string]
  data_status: enum:
    local
    web_researched
    mixed
    incomplete
  action_summary: list of safe user-visible strings
```

# PART 4 — Build Typed Tool Wrappers

Do not duplicate business logic. Wrap and call existing services.

## 4.1 Vehicle Search Tool

File: `vehicle_search_tool.py`

Purpose:

- Find vehicle manufacturer/model/variant.
- Resolve typo/fuzzy matches.
- Return multiple choices when model/variant is ambiguous.
- Use existing vehicle repository, vehicle-search orchestrator, and RAG retrieval where appropriate.

Input:

```python
VehicleSearchInput:
  query: string
  manufacturer: optional string
  model: optional string
  variant: optional string
  fuel_type: optional string
  body_type: optional string
  year: optional integer
```

Output:

```python
VehicleSearchData:
  matched_vehicles: list
  exact_match: bool
  ambiguous: bool
  suggested_choices: list
```

Rules:

- Never choose an ambiguous variant silently.
- If “Nexon” resolves to several fuel/variant choices and price/EMI is requested, ask user to select a variant.
- For generic queries, return shortlisted cars only when supported by data.

## 4.2 Vehicle Details Tool

File: `vehicle_details_tool.py`

Purpose:

- Get structured vehicle specs, model year, body type, fuel options, safety/features, and local pricing record.
- Distinguish model year, launch year, facelift/update, and upcoming status.

Rules:

- Never call model-year data “launch” unless launch metadata confirms it.
- Return data freshness information.
- Mark missing values as unavailable; do not invent.

## 4.3 Pricing Quote Tool

File: `pricing_quote_tool.py`

Purpose:

- Call the existing `PricingEngine`.
- Use existing city mapping, RTO rules, insurance rules, fee logic, and local vehicle-price records.
- Produce only deterministic estimated on-road price result.

Input:

```python
PricingQuoteInput:
  manufacturer: string
  model: string
  variant: optional string
  city: optional string
  state_code: optional string
  fuel_type: optional string
  ex_showroom_price: optional decimal
  include_zero_dep: bool
  include_dealer_handling: bool
```

Rules:

- If city/state is absent, ask user for city before quote calculation.
- If ex-showroom price/variant is missing, find it in local data.
- If unavailable, ask for exact variant or ex-showroom price.
- Do not let LLM estimate the price.
- Label every response “Estimated On-Road Price.”
- Include `last_updated`, `rule_effective_date`, assumptions, and disclaimer.
- Do not call external paid pricing APIs.

## 4.4 EMI Tool

File: `emi_tool.py`

Purpose:

- Call existing deterministic EMI module.
- Use reducing-balance formula.
- Show 3, 5, and 7-year EMI by default unless user asks specific tenure.

Input:

```python
EMIInput:
  on_road_price: decimal
  down_payment: optional decimal
  down_payment_percent: optional decimal
  loan_amount: optional decimal
  annual_interest_rate: optional decimal
  tenure_years: list[int]
```

Rules:

- Down payment cannot be negative or above on-road price.
- Use local configurable default interest rate only if the user does not supply one.
- Clearly label default interest-rate assumption.
- Handle zero-interest safely.
- Include principal, EMI, total interest, and total payment.

## 4.5 Comparison Tool

File: `comparison_tool.py`

Purpose:

- Compare two or more resolved vehicles.
- Compare only fields available from tools/local data.
- Include prices only if both cars have comparable data.
- Support price/EMI comparison only after city, variant, and required financing information are known.

Comparison fields:

```text
body type
fuel type
transmission
engine/range
mileage
seating
safety
key features
ex-showroom price
estimated on-road price
EMI
strengths
limitations
```

Rules:

- Do not declare an overall “winner” without explaining user-constraint reasoning.
- If user has not provided budget/use case, show neutral comparison and ask what matters most.
- Never compare mismatched model years without clearly displaying each year.

## 4.6 Vehicle Media Tool

File: `vehicle_media_tool.py`

Purpose:

- Call existing `vehicle_media` service.
- Return gallery only for positively identified vehicles.
- Do not return fake/mismatched car images.
- Gracefully return no gallery if media is unavailable.

## 4.7 Web Research Tool

File: `web_research_tool.py`

Purpose:

- Reuse existing DuckDuckGo search service only for vehicle research and references.
- Find references for year-wise launches, historical details, upcoming vehicle announcements, and specs missing from local data.

Rules:

1. Prefer official manufacturer Indian websites/newsrooms.
2. Then trusted automotive sources:
   - Autocar India
   - CarWale
   - CarDekho
   - ZigWheels
   - Overdrive
   - HT Auto
   - Times Drive.
3. Do not treat raw search snippets as verified facts.
4. Do not return DuckDuckGo result page URL as citation.
5. Validate actual destination URLs.
6. Separate `launched`, `upcoming`, `announced`, `facelift`, and `model-year`.
7. If sources conflict, return warning instead of silently choosing one.
8. Do not use web research for deterministic RTO/EMI calculation.
9. Cache historical web-research output safely with retrieval date and source metadata.
10. Do not expose raw scraping errors to the user.

# PART 5 — Agent Planner

Create `planner.py`.

The planner should be deterministic/rule-based first. Do not depend only on the LLM for deciding critical pricing, EMI, or verification steps.

Planner responsibilities:

1. Normalize Hindi, Gujarati, English, and mixed Roman-script user queries.
2. Extract intent and entities.
3. Decide tool sequence.
4. Detect missing required fields.
5. Return follow-up question instead of guessing.
6. Limit number of tool calls.
7. Prevent repeated loops.
8. Preserve conversational context safely.

Required planning rules:

## 5.1 Price query

```text

```

Plan:

```text

2. if variant ambiguous → follow-up
3. pricing_quote

6. response_builder
```


Plan:

```text

2. city/state normalization
3. pricing_quote
4. emi
5. vehicle_media optional
6. verifier
7. response_builder
```

## 5.3 EMI with missing fields

Example:

```text
“Nexon EMI batao”
```

Return only a concise follow-up:

```text
Nexon ka kaunsa variant, kaunsi city, aur kitna down payment rakhna hai?
```

Do not compute an estimate until minimum required fields are known.

## 5.4 Comparison query

Example:

```text
“Creta vs Seltos”
```

Plan:

```text
1. vehicle_search for Creta
2. vehicle_search for Seltos
3. vehicle_details for both
4. comparison
5. verifier
6. response_builder
```

If city/financing is not supplied, do not calculate on-road price/EMI. Offer an optional follow-up.

## 5.5 Year-wise launches query

Example:

```text
“2024 mein India mein kaun si SUV launch hui thi?”
```

Plan:

```text
1. local vehicle-history/local database search
2. web_research only if local evidence is incomplete
3. filter by year, India market, status=launched, category=SUV
4. verifier
5. response_builder with citations
```

Do not show “Dataset Verification Notice” if usable trusted web references are found.

## 5.6 Specific model query

Example:

```text
“2024 Creta details”
```

Plan:

```text
1. vehicle_search
2. vehicle_details
3. web_research only if needed for year-specific verified detail
4. vehicle_media optional
5. verifier
6. response_builder
```

# PART 6 — Agent Orchestrator

Create `orchestrator.py`.

Responsibilities:

1. Receive `AgentRequest`.
2. Load safe conversation context.
3. Call planner.
4. Return follow-up immediately if required fields are missing.
5. Execute planned tools in dependency order.
6. Enforce per-tool timeout and safe failure handling.
7. Store trace metadata for debugging without exposing private planner reasoning.
8. Call verifier.
9. Call response builder.
10. Return `AgentResponse`.

Requirements:

- Maximum tool-call count per request.
- No recursive tool loops.
- Per-tool timeout.
- Graceful degradation:
  - pricing fails → explain that pricing is unavailable, do not invent value.
  - gallery fails → still show verified text.
  - web research fails → use local data if sufficient.
  - ambiguous car → ask user to select.
- Do not execute arbitrary code, shell commands, file writes, or untrusted URLs.
- Do not expose stack traces to users.
- Preserve existing logging style but redact sensitive data.

# PART 7 — Verifier

Create `verifier.py`.

The verifier must inspect tool results before final response.

Mandatory checks:

1. All price/RTO/EMI figures must originate from pricing/EMI tools.
2. City must map to valid state or quote must be state-level only.
3. Vehicle/variant ambiguity must not be silently resolved.
4. References must have valid destination URLs.
5. Web launch references must support requested year and India market.
6. Upcoming cars must not be shown as launched.
7. Facelift/model-year update must not be called new launch without evidence.
8. No unsupported “live” or “exact dealer price” claim.
9. No hallucinated value exists in final text.
10. Conflicting tool/source results must produce a user-visible warning.
11. Missing data must remain marked unavailable.

If verification fails:

- return safe partial result where possible, or
- return follow-up question, or
- return user-safe error.

Never fabricate a complete-looking answer.

- return follow-up question, or
